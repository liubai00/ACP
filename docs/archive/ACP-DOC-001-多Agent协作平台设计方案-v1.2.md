# ACP 多 Agent 协作平台设计方案

日期 2026-11-08 · 作者 Alex Morgan

文档编号 ACP-DOC-001 · 版本 v1.2 · 留存于项目仓库 docs/ 目录，变更记录见文末

## 1. 目标与范围

本方案把飞书群、GitLab CI/CD、任务榜和每位开发者电脑上的个人 Agent 接成一个可观察、可审批的任务协作平台。任何人从飞书或平台入口发布需求，平台建单、派工、调度个人 Agent 执行，Agent 之间可以互相求助，结果经 GitLab 检查和人工批准后落地。

**要解决的问题**

- 需求散落在飞书聊天里，没有统一的任务记录和状态。
- 个人 Agent 只能被自己的主人使用，别人无法调用，Agent 之间无法协作。
- Agent 干活的过程是黑盒，没人知道它在做什么、卡在哪一步。
- 开发者电脑在内网，没有公网地址，平台无法主动联系它。

**目标**

- 一个需求从飞书群或任务榜进入，全程有唯一的任务 ID 和状态记录。
- 任务可以人工认领，也可以按规则自动派给某个开发者的 Agent。
- Agent 之间通过统一协议互相调用，调用经过平台，全程可见、可授权、可审计。
- 每一步的输入、输出、耗时在界面上可查，关键节点必须人工批准才能继续。
- 开发者电脑只需安装一个接入程序，出站连接即可工作。

**非目标**

- 不替代 GitLab 做代码评审和合并，平台只推进流程、不自动合并代码。
- 不自研 Agent 运行时，个人 Agent 用各自现有的工具（如 Claude Code）。
- 不在第一阶段做自动派工和 Agent 互相调用，先把主线跑通。

**验收标准**

| 场景 | 通过条件 |
| --- | --- |
| 飞书发布需求 | 群里 @机器人 一句话，10 秒内任务榜出现对应任务 |
| 开发者执行 | 认领后，开发者电脑上的 Agent 自动开始工作，进度在任务详情页实时更新 |
| CI 回执 | MR 流水线结束后 30 秒内，任务状态和飞书群同步更新 |
| 人工审批 | 任务到达审批节点时停住，飞书卡片点同意后才继续 |
| Agent 互相调用 | 甲的 Agent 向乙的 Agent 发起子任务，双方对话在任务详情页可见 |
| 断线恢复 | 开发者电脑断网 5 分钟内重连，未完成任务不丢失 |

## 2. 总体架构

平台分五层：入口、连接编排、网关、协调、执行。只有协调服务器和开发者电脑上的接入程序需要自研，其余用现成产品拼装。所有调用都经网关进入协调服务器，开发者电脑只发起出站连接。

![总体架构](images/01-总体架构.png)

*图：总体架构 · 五层，协调服务器与接入程序为自研*

飞书和 GitLab 的事件先到 n8n 的连接器，再经网关进入协调服务器；任务榜和接入程序直接经网关访问协调服务器。

**组件职责**

| 组件 | 职责 | 来源 | 说明 |
| --- | --- | --- | --- |
| 飞书群 | 发布需求、接收通知、点击审批卡片 | 现成 | 飞书自建应用，事件订阅用长连接模式，不需要公网回调地址 |
| 任务榜 Web | 看任务状态、认领、查看详情与 Agent 对话记录 | 自研，轻量前端 | 只读写协调服务器的 REST 接口 |
| n8n | 飞书与 GitLab 连接器、审批与通知流程、执行视图 | 现成，自托管 | 自带等待审批节点、GitLab 节点、MCP 客户端与服务端节点 |
| agentgateway | 统一入口、JWT 认证、CEL 授权、审计日志、多 MCP 聚合 | 现成，v1.7.x | 第一阶段可用普通反代替代，第三阶段必须上 |
| 协调服务器 | 确定性内核（任务库、状态机、派工、审批、事件）加协调 Agent 外壳，对外提供 A2A 与 MCP 服务端 | 自研 | Python + a2a-sdk，全平台唯一的事实来源 |
| 接入程序 | 登录、出站订阅、拉起个人 Agent、回传进度与产物 | 自研，CLI 守护进程 | 每台开发者电脑一份 |
| 个人 Agent | 实际改代码、跑测试、提 MR | 现成，Claude Code、Codex 等各人自选 | 通过接入程序适配，平台不限定哪一款 |
| GitLab | 代码托管、CI/CD、MR 评审 | 现成 | 通过 Webhook 回执，平台不替代它的合并权 |

**设计原则**

- 任务库是唯一事实来源，飞书、任务榜、n8n 都只是它的视图或入口。
- 所有调用经网关，不允许 Agent 之间私下直连。
- 开发者电脑只出站，平台永远不需要主动连入内网。
- 人在环路：认领和合并前的审批必须由人点确认。
- 协调服务对外是一个 Agent，对内是确定性内核加协调 Agent 外壳：状态、权限、审批由内核的代码裁决，大模型只能通过同一套工具提建议，按自主等级逐步放权。

## 3. 核心概念与数据模型

平台只有一种核心对象：任务。需求是根任务，拆出来的子任务是任务，一个 Agent 向另一个 Agent 求助也是任务。任务状态直接采用 A2A 1.0 的八个状态，不另造一套，这样协调服务器对外的 A2A 接口不需要做状态映射。

**实体**

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| 任务 Task | id、parent\_id、标题、描述、类型（需求 / 子任务 / 求助）、state、负责人或负责 Agent、来源（飞书 / 任务榜 / Agent）、涉及的仓库列表、各仓库的分支与 MR 链接、创建人、时间戳 | 树形结构，根任务就是一条需求；A2A 的 task id 和平台的任务 id 是同一个 |
| Agent 注册 Agent | agent\_id、所属成员、Agent Card 原文、技能列表、在线状态、最后心跳 | 接入程序登录时上报自己的 Agent Card，平台据此派工和展示“谁在线” |
| 成员 Member | user\_id、飞书 open\_id、GitLab 用户名、角色（开发者 / 评审者 / 管理员）、团队 | 登录身份，也是 JWT 里 claims 的来源 |
| 审批 Approval | task\_id、卡点（认领 / 合并 / 高风险操作）、发起者、审批人、结论、时间 | 对应 n8n 的等待节点和飞书审批卡片 |
| 事件 Event | task\_id、序号、类型、触发者、载荷 | 只追加不修改；任务详情页的时间线和 A2A 的流式更新都从这里读 |
| 消息 Message | task\_id、发送方（人或 Agent）、内容、附件 Artifact | A2A 的 Message 和 Artifact 落库，Agent 之间的对话就存在这里 |

**任务状态在平台里的含义**

| A2A 状态 | 平台含义 | 谁触发 |
| --- | --- | --- |
| submitted 已提交 | 建单完成，等待认领或派工 | 飞书 / 任务榜 / 发起求助的 Agent |
| working 进行中 | 已有负责人，Agent 正在执行 | 接入程序 |
| input-required 待补充 | Agent 需要人补充信息才能继续 | Agent |
| auth-required 待授权 | 到达审批卡点，等人批准（如合并前） | 协调服务器 |
| completed 已完成 | MR 已合并，或需求方确认验收 | 审批人 / 发布者 |
| failed 失败 | CI 连续失败超过重试次数，或 Agent 报错退出 | 协调服务器 |
| canceled 已取消 | 发布者或管理员主动取消 | 人 |
| rejected 已拒绝 | 超出 Agent 能力范围，或触发安全规则被平台拒绝 | Agent / 协调服务器 |

![任务状态机](images/02-任务状态机.png)

*图：任务状态机 · 8 个状态，4 个终态*

取消可以从任何未结束的状态发起，图中只画了一条；completed、failed、canceled、rejected 是终态，到达后不再变化，要返工就新建任务。

## 4. 关键流程

一条需求从飞书进入到 MR 合并要经过六段流程。每一段都写进任务库的事件表，任何一段中断都能从上一个状态恢复。

![主流程](images/03-主流程.png)

*图：主流程 · 7 步，2 个判断，2 条回环*

CI 未通过最多回环 2 次，再失败转 failed；审批拒绝没有次数限制，但每次都会通知负责人。

**4.1 需求发布与建单**

1. 成员在飞书群 @机器人 发一句话，或在任务榜填表单。
2. n8n 飞书连接器通过长连接收到事件，按事件 ID 去重后调用协调服务器的建单接口。
3. 协调服务器建任务，状态 submitted，写事件，回飞书群一张任务卡片（任务号、链接、认领按钮）。
4. 任务榜实时出现这条任务。

Agent 在执行中发起的求助也走同一个建单接口，只是 parent\_id 指向原任务。

**4.2 派工与认领**

| 方式 | 怎么工作 | 阶段 |
| --- | --- | --- |
| 人工认领 | 点飞书卡片或任务榜上的认领按钮，负责人写入，状态转 working | 第一阶段 |
| 规则派工 | 按仓库目录归属、技能标签、Agent 在线状态选人，卡片发给该成员，成员点“接受”后才转 working | 第二阶段 |
| Agent 自荐 | 协调服务器把任务技能需求和在线 Agent 的 Agent Card 匹配，匹配度最高的 Agent 所属成员收到推荐 | 第三阶段 |

三种方式都以成员本人点确认为准，平台不会在没有人确认的情况下在某人电脑上开始执行。

**4.3 开发者端执行**

1. 接入程序登录后，向协调服务器发一条 A2A 流式消息“订阅我的任务”，这条连接长期挂着。派给该成员的任务以状态更新的形式推下来。
2. 收到任务后，用本机 Atlas 定位任务涉及的仓库，在每个仓库准备任务分支和隔离工作区，组装上下文（任务描述、关联 MR、各仓库的检查命令）。
3. 无头模式启动个人 Agent，把它的输出事件转成 A2A 状态更新和消息，实时回传。
4. Agent 需要人补充信息时，任务转 input-required，飞书通知负责人，回复后恢复。
5. 完成后用 Atlas 跑各仓库检查，再逐个仓库推分支、开 MR，MR 链接作为 Artifact 回传。
6. 断线后用任务 ID 重新订阅，未完成的任务保持 working；30 分钟没有心跳则回收到 submitted 并通知负责人。

**4.4 Agent 互相调用**

![Agent 互相调用时序](images/04-Agent互调时序.png)

*图：Agent 互相调用时序 · 6 步*

甲的 Agent 看到的只是一个子任务的状态和产物，它不知道也不需要知道乙的电脑在哪里。

1. 甲的 Agent 判断需要后端配合，调用平台的求助工具，带上目标技能或目标成员。
2. 网关校验甲有权发起求助；协调服务器建子任务，parent 指向原任务，类型为求助。
3. 子任务按 4.2 派给乙。乙若事先开启了“自动接受来自本团队的求助”，乙的 Agent 直接开工；否则等乙点接受。
4. 乙的 Agent 执行，进度回流到子任务；甲的 Agent 订阅子任务，完成后拿到 Artifact 继续自己的工作。
5. 双方所有消息存入消息表，任务详情页按时间线展示。

防止失控的三条规则：子任务最多嵌套 2 层；一个根任务最多 5 个子任务；同一对 Agent 之间不允许互相求助形成环。超出即 rejected。

**4.5 CI 回执与审批**

1. MR 创建、更新和流水线事件通过 GitLab Webhook 到 n8n，按分支名里的任务号匹配任务。
2. 流水线失败：失败日志作为消息回传给 Agent，Agent 自动修复，最多重试 2 次；仍失败转 failed 并通知负责人。
3. 流水线通过：任务转 auth-required，n8n 等待节点挂起，飞书审批卡片发给评审者。
4. 评审者同意：平台在 MR 上标记批准，合并由人或 GitLab 规则完成；所有相关仓库的 MR 合并事件都回来后转 completed，飞书群汇报。
5. 评审者拒绝：附意见回到 working，Agent 继续修改。

**4.6 异常与恢复**

| 异常 | 处理 |
| --- | --- |
| 飞书或 GitLab 回调重复送达 | 事件 ID 去重表，重复事件直接丢弃 |
| 接入程序断线 | 按任务 ID 重新订阅；30 分钟无心跳的任务回收到 submitted |
| 个人 Agent 卡死 | 接入程序设单任务超时（默认 60 分钟），超时杀进程，任务转 input-required 并通知 |
| 协调服务器重启 | 状态全在数据库，订阅由客户端自动重建 |
| n8n 流程执行失败 | n8n 自身重试，错误工作流通知管理员 |
| 子任务嵌套过深或数量过多 | 超出 4.4 的上限直接 rejected，通知发起方 |

## 5. 接口设计

协调服务器对外有三个面：A2A 给 Agent 之间对话，MCP 给个人 Agent 当工具，REST 给任务榜和 n8n。三个面背后是同一套任务逻辑，全部经网关进入。入站 Webhook 由 n8n 接收，归一化后再调 REST。

**5.1 A2A 接口**

协调服务器本身是一个 A2A Agent，Agent Card 放在 `/.well-known/agent-card.json`，经网关后 url 自动改写为网关地址。传输用 JSON-RPC over HTTP，流式用 SSE；声明 streaming 为 true，pushNotifications 为 false，因为开发者电脑没有可回调的公网地址。

| 技能 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| subscribe\_assignments | 接入程序订阅派给本人的任务 | 成员身份（来自 JWT）、Agent Card | 一个长期 working 的订阅任务，新派工以状态更新推送 |
| create\_task | 建单，含 Agent 发起的求助子任务 | 标题、描述、parent\_id、目标技能或成员 | Task，状态 submitted |
| report\_progress | 回传进度、消息、产物 | task\_id、消息、Artifact | Task 状态更新 |
| request\_input | 请求人工补充 | task\_id、问题 | Task，状态 input-required |

用到的协议方法：SendMessage、SendStreamingMessage、GetTask、SubscribeToTask、CancelTask。gRPC 和 HTTP+JSON 绑定第一版不启用。

**5.2 MCP 工具**

给个人 Agent 和 n8n 调用。经 agentgateway 聚合后，工具名会带上 `<server>-<port>_` 前缀，写 Agent 提示词时要用聚合后的名字。

| 工具 | 作用 | 谁能调 |
| --- | --- | --- |
| list\_tasks | 按状态、负责人、仓库查任务 | 所有成员 |
| get\_task | 任务详情含消息时间线 | 所有成员 |
| claim\_task | 认领 | 成员本人 |
| update\_task | 更新状态、分支、MR 链接 | 负责人 |
| post\_message | 给任务发消息或附件 | 负责人、求助发起方 |
| ask\_agent | 发起求助子任务 | 负责人，第三阶段开放 |
| request\_approval | 触发审批卡点 | 负责人 |

“谁能调”中按工具名的部分由网关的 CEL 规则执行；按数据判断的部分（是否负责人）由协调服务器执行，因为 CEL 规则读不到工具参数。

**5.3 REST 接口**

| 方法与路径 | 用途 | 调用方 |
| --- | --- | --- |
| POST /api/tasks | 建单 | n8n、任务榜 |
| GET /api/tasks | 列表，支持按状态、负责人、仓库筛选 | 任务榜 |
| GET /api/tasks/{id} | 详情与时间线 | 任务榜 |
| GET /api/tasks/{id}/stream | SSE，任务详情页实时更新 | 任务榜 |
| POST /api/tasks/{id}/claim | 认领 | 任务榜、n8n（飞书卡片按钮） |
| POST /api/tasks/{id}/approvals/{gate} | 审批结论 | n8n（飞书审批卡片） |
| POST /api/events/gitlab | 归一化后的 GitLab 事件 | n8n |
| POST /api/events/feishu | 归一化后的飞书事件 | n8n |
| GET /api/agents | 在线 Agent 与技能列表 | 任务榜 |

**5.4 Webhook 契约**

| 来源 | 事件 | 校验 | 幂等键 | 任务匹配 |
| --- | --- | --- | --- | --- |
| GitLab | Merge Request Hook、Pipeline Hook、Push Hook | Secret Token | X-Gitlab-Event-UUID | 分支名 `acp/<任务号>-<摘要>` |
| 飞书 | im.message.receive\_v1（@机器人）、card.action.trigger（卡片按钮） | 长连接模式自带鉴权 | event\_id | 卡片按钮携带 task\_id；新消息建新任务 |

出站调用：飞书发消息和更新卡片 API；GitLab 的 MR 评论、审批、commit status API。两者都由 n8n 节点完成，协调服务器不直接持有飞书和 GitLab 的凭证。

## 6. 开发者端接入程序

接入程序是装在每台开发者电脑上的命令行守护进程。它只做四件事：登录、订阅任务、在隔离环境里拉起个人 Agent、把进度和产物回传。它不包含任何业务逻辑，换一款 Agent 只需换一个适配器。

**运行方式**

| 项 | 设计 |
| --- | --- |
| 形态 | 单个可执行文件，开机自启，托盘图标显示在线和当前任务 |
| 登录 | 浏览器走飞书 OAuth，换平台签发的 JWT，有效期 7 天，到期自动刷新 |
| 注册 | 登录后上报本机 Agent Card：技能标签、能处理的仓库、Agent 类型与版本 |
| 订阅 | 一条 A2A 流式连接长期挂着，每 30 秒心跳；断线按指数退避重连，用 SubscribeToTask 续上 |
| 并发 | 默认同时只跑 1 个任务，可配置到 3 |
| 配置 | 本地一个 YAML：平台地址、仓库根目录、Agent 适配器、超时、是否自动接受本团队求助 |

**执行一个任务的步骤**

1. 收到派工，回传 working。
2. 调用本机 Atlas 定位任务涉及的仓库（可能不止一个），在每个仓库准备以任务号命名的任务分支和隔离工作区，分支名 `acp/<任务号>-<摘要>`。
3. 组装上下文文件：任务描述、历史消息、关联 MR、Atlas 给出的仓库清单和各仓库的检查命令。
4. 通过适配器无头启动个人 Agent，工作目录锁在 Atlas 准备好的工作区内，平台的 MCP 工具作为 Agent 的工具注入。
5. 解析 Agent 的输出事件流，每个工具调用和阶段性结论转成一条 A2A 消息回传。
6. Agent 结束后用 Atlas 运行各仓库的检查；有提交则逐个仓库推分支并开 MR，MR 链接作为 Artifact 回传；无提交则回传 Agent 的结论并转 input-required。
7. 清理工作区，回到等待。

**Agent 适配器**

| Agent | 启动方式 | 输出解析 | 阶段 |
| --- | --- | --- | --- |
| Claude Code | 无头模式加流式 JSON 输出，MCP 配置指向网关 | 按事件类型映射到进度消息、工具调用、最终结论 | 第一阶段 |
| Codex | 非交互模式加 JSON 事件输出，MCP 配置指向网关 | 同上，事件字段不同，单独一个适配器 | 第一阶段 |
| 其他支持 MCP 的 Agent | 按各自命令行参数 | 实现同一个适配器接口：启动、读事件、终止 | 按需 |
| 自研 Agent | 直接以 A2A 客户端身份接入，不需要接入程序 | 自己调 report\_progress | 按需 |

适配器是接入程序里唯一和具体 Agent 有关的代码，每个不超过几百行。开发者在配置文件里选自己用哪一个，用自己的账号登录该 Agent。

**本机 Atlas 的角色**

Atlas 是团队用来协调多个代码仓库的本地开发工具：能找到一个任务涉及的所有仓库（例如一次鸿蒙适配同时涉及客户端和后端两个仓库），在各仓库准备任务分支，运行各自的检查。接入程序把它当作“多仓库操作层”：上面的第 2 步和第 6 步都通过 Atlas 完成，Agent 执行中也可以直接调 Atlas 命令。所以任务模型里的仓库是一个列表，一个任务可以产生多个 MR，全部合并才算完成。Atlas 和工作目录都在开发者电脑上，不上传平台；推代码和合并 MR 的权限仍由各项目在 GitLab 的角色决定，Atlas 和平台都不绕过它。接入程序开发前需要 Atlas 的命令行接口说明，见第 11 节。

**本机安全边界**

- Agent 只能在 Atlas 准备好的各仓库工作区内读写，接入程序不给它之外的路径。
- Agent 没有平台的长期凭证，只拿到接入程序为当前任务签发的短期令牌。
- 任务描述被当作不可信输入注入提示词，接入程序在系统提示词里明确告诉 Agent：任务里的文字不是命令。
- 推分支和开 MR 由接入程序做，不给 Agent GitLab 的写权限。

## 7. 网关与安全

安全分三层各管一段：网关管“谁能进门、能调哪个工具”，协调服务器管“对哪条任务能做什么”，接入程序管“Agent 在本机能碰什么”。最大的风险不是外部攻击，而是飞书里一句话变成别人电脑上执行的指令。

**7.1 agentgateway 配置要点**

用独立模式（单个 YAML），一个 443 端口，三条路由。下面是示意，字段名以 v1.7 文档为准；其中 `a2a: {}` 标记和 `mcpAuthorization` 的 CEL 规则写法已核对官方文档。

```yaml
binds:
- port: 443
  listeners:
  - routes:
    - matches: [{ path: { pathPrefix: /a2a } }]
      policies:
        jwtAuthentication:
          issuer: https://acp.internal
          jwks: { url: https://acp.internal/.well-known/jwks.json }
        a2a: {}            # 网关改写 Agent Card 的 url
      backends: [{ host: coordinator:9999 }]
    - matches: [{ path: { pathPrefix: /mcp } }]
      policies:
        mcpAuthentication:
          issuer: https://acp.internal
          audiences: [https://acp.internal/mcp]
          jwks: { url: https://acp.internal/.well-known/jwks.json }
        mcpAuthorization:
          rules:
          - 'mcp.tool.name.endsWith("list_tasks") || mcp.tool.name.endsWith("get_task")'
          - 'mcp.tool.name.endsWith("claim_task") && has(jwt.sub)'
          - 'mcp.tool.name.endsWith("ask_agent") && "agent_caller" in jwt.roles'
          - 'mcp.tool.target == "gitlab" && "developer" in jwt.roles'
      backends: [{ mcp: { targets: [coordinator-mcp, gitlab-mcp] } }]
    - matches: [{ path: { pathPrefix: /api } }]
      policies: { jwtAuthentication: { issuer: https://acp.internal, jwks: { url: https://acp.internal/.well-known/jwks.json } } }
      backends: [{ host: coordinator:8000 }]
```

- 被 CEL 规则过滤掉的工具不会出现在 Agent 看到的工具列表里，Agent 根本不知道它们存在。
- CEL 规则读不到工具参数，所以“只能改自己负责的任务”这类判断在协调服务器里做。
- 网关的访问日志接 OpenTelemetry，每次调用都能对应到人、Agent 和任务号。
- JWT 和 CEL 在 a2a 标记路由上的完整生效需要在第一次搭建时验证，官方 A2A 页面只演示了 CORS。

**7.2 身份与令牌**

| 令牌 | 颁发给谁 | 有效期 | 关键 claims |
| --- | --- | --- | --- |
| 成员令牌 | 任务榜登录用户、接入程序 | 7 天，可刷新 | sub、roles、teams |
| Agent 任务令牌 | 接入程序为每个任务向平台申请，交给个人 Agent | 任务超时时长，最多 2 小时 | sub、act=agent、task\_id、roles 被收窄 |
| 服务令牌 | n8n 调协调服务器 | 长期，定期轮换 | sub=n8n、roles=connector |

身份源是飞书自建应用的 OAuth（已授予用户身份权限），平台自己签发 JWT。Agent 的调用带 act=agent，审计时能区分人和 Agent。

**7.3 权限矩阵**

| 操作 | 任意成员 | 任务负责人 | 评审者 | 管理员 | 他人的 Agent |
| --- | --- | --- | --- | --- | --- |
| 查看任务 | 可 | 可 | 可 | 可 | 可（同团队） |
| 建单 | 可 | 可 | 可 | 可 | 可（仅求助子任务） |
| 认领 | 可 | — | 可 | 可 | 否 |
| 更新任务、发消息 | 否 | 可 | 否 | 可 | 否 |
| 发起求助 | 否 | 可 | 否 | 可 | 否 |
| 审批合并 | 否 | 否 | 可 | 可 | 否 |
| 取消任务 | 发布者可 | 否 | 否 | 可 | 否 |

**7.4 提示注入与失控防护**

- 任务文本始终作为不可信输入注入，系统提示词固定在接入程序里，平台不允许通过任务修改它。
- 两个人工卡点不可绕过：开始执行前成员本人确认，合并前评审者确认。
- Agent 的工具是白名单，由网关 CEL 执行；删除分支、改 CI 配置、合并 MR 这类工具不开放给 Agent。
- Agent 没有 GitLab 写凭证，推分支和开 MR 由接入程序代做。
- 求助子任务有深度、数量和环检测上限，防止 Agent 之间无限互相派活。
- 飞书和 GitLab 的凭证只在 n8n 和接入程序里，不进任何提示词。
- 所有调用和状态变更进事件表和网关日志，建议保留 180 天。

## 9. 技术选型与部署拓扑

所有服务端组件容器化。第一阶段在云上一台 8 核 16 GB 的服务器用 docker compose 就能跑全套，由你部署，部署手册随第一阶段交付；第三阶段流量和权限复杂度上来后迁到 Kubernetes，agentgateway 有现成的 Gateway API 控制器。

**选型**

| 组件 | 选型 | 版本策略 | 理由 |
| --- | --- | --- | --- |
| 协调服务器 | Python 3.12 + FastAPI + a2a-sdk（A2A 1.0）+ 官方 MCP Python SDK | a2a-sdk 锁小版本 | A2A 官方 SDK 中 Python 最成熟，n8n 和 Agent 生态多为 Python |
| 数据库 | PostgreSQL 16 | — | 事务加 JSONB 存 Agent Card 和事件载荷；用 SKIP LOCKED 做队列，LISTEN/NOTIFY 做广播，不引入 Redis |
| 流程与连接器 | n8n 自托管，队列模式，Postgres 后端 | 锁大版本 | 等待节点、GitLab 节点、MCP 客户端与服务端节点现成 |
| 网关 | agentgateway v1.7.x 独立模式 | 锁 1.7 | 第一阶段可用 Caddy 反代加 JWT 校验代替 |
| 任务榜 | React + Vite 或 Vue 3 单页应用 | — | 团队熟哪个用哪个 |
| 接入程序 | Go 单二进制（a2a-go SDK），或 Python 打包 | — | 开发者电脑有 Windows 和 macOS，单文件分发最省事 |
| 身份 | 飞书 OAuth 换自签 JWT，RS256，公布 JWKS | — | 网关和协调服务器都能离线验签 |
| 可观测 | OpenTelemetry 导向 Grafana（Loki、Tempo） | — | agentgateway 和 n8n 都原生支持 |
| 协调 Agent（可选） | 协调服务器内的大模型调用模块，用你提供的模型 key | 可开关 | 带工具调用的 Agent 循环，只通过内核工具操作，按自主等级逐步放权，见下文 |

**协调服务器里的大模型用途**

协调服务对外就是一个 A2A Agent，对内分两层：确定性内核负责执行和把关，协调 Agent 负责理解和建议。大模型不做状态决策，第一阶段不配 key 也能跑。

| 层 | 做什么 | 怎么做决定 |
| --- | --- | --- |
| 内核 | 任务库、状态机、权限矩阵、审批卡点、派工规则、幂等去重、事件日志 | 确定性代码，可测试，每个状态变化都有明确的触发条件 |
| 协调 Agent | 理解需求、拆解任务、推荐派工、归类失败、回答人的提问、替 Agent 之间传话 | 大模型，但只能通过内核暴露的同一套 MCP 工具操作，和其他 Agent 一样受权限矩阵约束 |

协调 Agent 没有后门：建单也是调 create\_task，派工也是调 assign\_task，工具里的校验它绕不过去。它的输出本质上是建议，落地要么过内核规则，要么过人确认，一句话概括就是模型提议、规则裁决。

**协调 Agent 的触发场景**

它不常驻在每个事件上，Webhook、心跳、普通状态更新都不经过它，只在六种场景被叫醒：

| 场景 | 它做什么 | 第一阶段等级 | 目标等级 |
| --- | --- | --- | --- |
| 新需求进来 | 把一句话整理成结构化任务，建议拆分、涉及仓库、派给谁 | L0 | L1 |
| Agent 发起求助 | 选目标 Agent，把必要上下文整理好传过去 | 不开放 | L1 |
| Agent 卡在待补充 | 先从任务历史和相关 MR 找答案，找不到再问人 | L0 | L1 |
| CI 失败 | 把日志归类为 Agent 可自修或需人介入，决定重试还是升级 | L0 | L1 |
| 飞书里 @它 提问 | 回答任务进度、谁能做某事这类问题 | L1，只读 | L1 |
| 定时巡检 | 找出卡太久的任务、离线的 Agent，主动提醒 | L1，只通知 | L2 |

**自主等级**

每类动作单独设等级，不做全局开关。L0 只建议：生成建议写进卡片，人点确认才执行。L1 先做再通知：自动执行并通知相关人，可一键撤销。L2 全自动：不通知，只记日志。第一阶段全部 L0 或只读，第二阶段把建单解析和失败归类升到 L1，第三阶段再逐项评估 L2。“更聪明”是逐步放权的结果，不是一开始就赌模型靠谱。

**实现**

一个带工具调用的 Agent 循环，工具是内核的 MCP 工具加几个只读上下文查询（任务历史、Agent 注册表、仓库清单）。每次触发是一次独立调用，带任务号写进事件表，建议和执行分开记录，事后能回答“为什么派给了谁”。key 放在服务器环境变量或密钥管理里，不进数据库、不进提示词、不下发给开发者电脑。个人 Agent 用开发者自己的账号，和这个 key 无关。第三阶段可以让 agentgateway 代理大模型 API，由网关统一持有 key 并计量用量。

**部署拓扑**

| 阶段 | 形态 | 内容 |
| --- | --- | --- |
| 第一阶段 | 云上单机 docker compose，只开 443 | coordinator、postgres、n8n、board、caddy 或 agentgateway |
| 第三阶段 | Kubernetes | agentgateway 控制器 + Gateway API；coordinator 多副本，SSE 订阅靠 Postgres LISTEN/NOTIFY 跨副本广播；n8n 主节点加 worker |

**网络要求**

- 协调服务器在云上，安全组只开 443，SSH 限制来源 IP。
- 开发者电脑在公司内网，通过互联网出站访问服务器的 443。内网防火墙需放行到该地址的 HTTPS 出站；若内网强制走代理，接入程序支持 HTTPS 代理配置。
- SSE 长连接要求代理和防火墙不在 60 秒内切断空闲连接，接入程序 30 秒一次心跳可以覆盖；被切断也只是重连，不丢任务。
- 飞书事件是服务器到飞书的出站长连接，服务器不需要被飞书反向访问。
- 你们自部署的线上 GitLab 到云服务器的 Webhook 已确认可达，走 443 入站。
- 个人 Agent 推代码走开发者电脑到 GitLab 的既有通路，不经平台。
- 开发者电脑不需要任何入站端口。具体的内网放行清单和代理配置步骤放在部署手册里。

**运维**

- Postgres 每日全量备份，保留 30 天。
- n8n 工作流导出为 JSON 进 Git 仓库，和协调服务器代码一起版本化。
- 接入程序自带自更新，由协调服务器下发最低版本要求。

## 11. 风险与待确认问题

最大的技术风险是两个开源项目都在快速演进，最大的落地风险是没人认领任务。前者靠锁版本和把协议细节封在协调服务器一层，后者靠小组试点。

**风险**

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| A2A 和 agentgateway 版本快速演进 | 接口变更返工 | 锁版本；协议细节只出现在协调服务器和接入程序的适配层 |
| agentgateway 对 a2a 路由的 JWT 和 CEL 生效未经验证 | 第三阶段安全模型落空 | 第一阶段搭环境时就验证；不行则用外部鉴权或协调服务器自己校验 |
| “订阅任务”是对 A2A 流式语义的借用 | SDK 升级可能改变长连接行为 | 订阅封成独立模块，必要时切换到自定义 WebSocket |
| 飞书长连接的连接数和频率限制 | 高峰丢事件 | n8n 侧队列加去重；超限降级为 Webhook 模式 |
| 开发者电脑休眠或关机 | 任务卡在 working | 30 分钟无心跳回收并通知；任务榜显示 Agent 离线 |
| 提示注入 | 错误代码进 MR | 双人工卡点、工具白名单、不自动合并 |
| 团队接受度低 | 任务无人认领 | 第一阶段只在一个小组试点，跑通后再推 |
| 协调服务器单点 | 全平台停止 | 第一阶段接受；第三阶段多副本 |

**已确认的事项**

| 问题 | 结论 | 对设计的影响 |
| --- | --- | --- |
| 个人 Agent | 各人自用的 Claude Code、Codex 或其他，不统一 | 接入程序提供多个适配器，第一阶段先做 Claude Code 和 Codex |
| 本机 Atlas | 团队的多仓库协调工具：定位任务涉及的仓库、在各仓库准备任务分支、运行各自检查；推送和合并权限仍由 GitLab 角色决定 | 接入程序通过 Atlas 操作仓库；任务模型支持跨多个仓库、多个 MR |
| GitLab | 自部署的线上实例，Webhook 可达协调服务器 | 走 443 入站，不需要额外打通 |
| 网络 | 协调服务器在云上，开发者电脑在公司内网 | 维持出站订阅方案；内网只需放行到服务器 443 的出站，步骤写在部署手册 |
| 飞书 | 自建应用，已授予用户身份权限 | OAuth 登录和以用户身份发消息都可用 |
| 开发者电脑 | macOS 和 Windows 都有 | 接入程序用 Go 单二进制，两个平台各出安装包 |
| 试点 | 一个小组，Mac 与 Windows 各两台 | 第一阶段验收门按这个规模 |
| 部署 | 云服务器，由你亲自部署 | 部署手册是第一阶段交付物 |
| 大模型 | 你提供 key | 确定性内核加协调 Agent 外壳，按自主等级逐步放权，见第 9 节 |
| 人力 | 各阶段由你们团队承担 | 工期由你们按投入自定 |
